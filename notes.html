两套可复用的架构方法论

这是两篇工程方法论笔记，配一张合成架构示意图。所有示例均为合成演示， 不对应任何真实品牌、门店或线上系统；只讲模式，不写真实数据。

示意图：外部系统经「端口（接口契约）」与「适配器（Mock / Live）」解耦， 业务只依赖端口；下游为合成门店与评测看板。仅作方法论演示。

一、端口-适配器（Ports & Adapters）接入外部系统

问题

业务系统常要对接外部系统（如 ERP、上游模型）。若业务代码直接调用某家具体实现的 SDK / 接口，一旦供应商替换或接口变更，业务层要跟着大改，且本地无法脱离外部依赖做测试。

模式

把外部能力抽象成端口（接口契约），具体对接写成适配器： 一个 Mock 适配器（合成镜像，is_live = false）用于本地与测试； 一个 Live 适配器（真实对接，is_live = true，占位未接入）用于生产。 业务只依赖端口，不依赖实现。

// 端口：仅定义契约
interface ErpSource {
  isLive: boolean;
  fetchStores(): Store[];
}

// 适配器 A：合成镜像（本地 / 测试默认）
class MockErpSource implements ErpSource {
  isLive = false;
  fetchStores() { return SAMPLE_MIRROR; }   // 合成门店，与真实无关
}

// 适配器 B：真实对接（占位，未接入）
class LiveErpSource implements ErpSource {
  isLive = true;
  fetchStores() { /* TODO: 接真实端点 */ }
}

收益

  • 可测试：Mock 适配器让整条链路在零外部依赖下跑通与回归；
  • 可替换：换供应商只需新增一个适配器，业务层零改动；
  • 数据安全：本地永远跑合成镜像，真实接口凭据不进代码、不进公开仓。

二、门店执行闭环（合成参考实现）

问题

总部把标准动作做成「作战卡」下发给每家门店，门店执行后由门店验收，形成 下发 → 执行 → 验收 的管控闭环。难点不在"发下去"，而在覆盖完整与状态不可跳步。

状态机

dispatched ──执行──▶ executed ──验收──▶ accepted
（已下发）            （已执行）          （已验收）

推进必须依次走过，从 dispatched 直接到 accepted 会被拦截—— 避免"看起来闭环了其实没执行"的假闭环。

全量下发与试点

  • 合成门店：演示品牌 A / B / C / D 四市共 12 家（与 hunkon_rag 真相源一致）；
  • 3 张作战卡 × 12 家 = 36 条下发记录，缺一条就是覆盖漏洞；
  • 试点门店跑通全闭环验证流程，其余门店先只下发。

把"闭环不破洞"做成断言

# 全量下发计数、合法推进、非法跳过拦截，均有单测覆盖
seed_loop()                      # 12 家 × 3 卡 = 36 下发
stats()["by_status"]["accepted"] # 试点门店全闭环数
advance(did, "accepted")         # 从 dispatched 直接验收 → 抛错

完整代码见 store_tool 的 app/store_loop.py 与 tests/test_store_loop.py，均为合成数据。
