接入 AI

sensenova-gateway

统一模型调用层 · 多模型路由 · 530 行零依赖

零依赖的本地 OpenAI 兼容网关，把 N 个 SenseNova API key 聚合成一个端点。

  • 多账号轮询（按 5h 窗口内用量最少）
  • 429/401 自动切换 + 冷却隔离
  • 别名映射 + SSE 流式转发
  • 16 项离线自测全通过
为什么改造：多账号配额不够、429 频发，AI 调用不稳定。
场景价值：给上层 prompt-craft / llm-wiki / ai-native-team 提供稳定模型底座。
单独用：任何需要多 key 稳定调用的团队可直接用（16 项自测）。

prompt-craft

Prompt 工程 · 模板体系 · 1189 行

AI 提示词写法库（图像 + 视频），从"一句话许愿"到"一句话下订单"的实战手册。

场景价值：让 AI 内容产出一遍过，案例沉淀进 kb-cli / llm-wiki。
单独用：任何做 AI 图像/视频的团队可直接用这套方法论。

管理知识

kb-cli

私有知识库 · RAG 检索 · 158 行零依赖

零依赖的本地知识库检索工具，把散落的 markdown 文档重组为「多子库 × 多层」结构。

  • 三层架构：L1 速查 / L2 导航 / L3 原始
  • 多子库拆分 + 单文件 158 行检索器
  • 自动同步聊天记录，智能分类到不同子库
  • UTF-8 强制输出 + 双写，Windows 不炸
为什么改造：文档越攒越多找不到，知识是死数据。
场景价值：作为 llm-wiki 编译层的检索底座，让知识与 AI 共用。
单独用：任何「文档多找不到」的团队可直接用（零依赖开箱即用）。

编译知识

llm-wiki

RAG 知识库 · 概念聚合 · 增量编译

raw → wiki → RAG 双轨知识编译层：把 1,600+ 篇原始资料自动编译成可导航的 wiki 知识层（实体 / 概念 / 对比 / 综合）。

  • 概念聚合：同一概念多源合并一页，来源逐条列源（80+ 源）
  • 双向链接：entity ↔ concept ↔ synthesis 层级互链
  • 增量局部重编：--local-rebuild 实测仅重编 4 页
  • lint 巡检：锚定 / 死链 / 孤立页 / 冲突 / 死循环，锚定 100%
为什么改造：原始资料不可导航，RAG 泛词塌缩。
场景价值：在 kb-cli 之上加编译层，人工与 RAG 共用可导航产物。
单独用：上千篇原始资料的团队可复用这套编译方法论。

技术选型

我为什么用关键词 + IDF 而不是向量检索

kb-cli 设计决策 · 8 分钟阅读

在 kb-cli 里我用了关键词 AND 匹配 + IDF 加权，没上向量检索——这是当前场景下的刻意选择，不是技术债。

最早排序用绝对词频，结果 59.8% 的文档被"运营""系统"这类泛词压到同一个主题下；加 IDF 给到处出现的泛词降权后，这种塌缩就消失了。

垂直语料用词稳定、查询都是短的精确查询、还要零依赖可交付——这三条让我暂时不上向量；等语料过万、或出现"用户问法和文档用词对不上"的语义鸿沟时，再上本地 embedding 做混合检索。
