为什么知识库调取要用 LLM × RAG，而不是单用其一

llm-wiki 设计决策 · 约 8 分钟阅读

做知识库调取时，最容易踩的两个极端：单用 LLM 让它凭训练数据回答，结果就是幻觉——模型根本没有你的业务事实，只能靠猜；单用 RAG 只给你一堆文档列表，那不是答案，是原材料。我做的是一套 LLM × RAG 知识库调取系统：LLM 负责组织知识，RAG 负责精确召回，命中页作为上下文喂给 LLM，生成有依据、可溯源的答案。

先讲我真实踩过的坑：泛词塌缩

最早检索器的排序用的是绝对词频——一个词在某篇文档里出现几次，就给这篇加几分。拿它跑 2,000 多篇同领域语料，问题非常明显：59.8% 的文档被"运营""管理""系统"这类到处都出现的泛词，压到了同一个主题下面，真正有区分度的词——"私域""复购""会员码"——反而排不上来。

修正办法是加 IDF（逆文档频率）：一个词越普遍，权重越低；越罕见、越能代表主题，权重越高。改成 TF × IDF 之后，文档被均匀地分散回各自的主题，泛词塌缩就消失了。

为什么 LLM 也要参与？因为「可导航」和「可调取」是两回事

原始资料保真但不可导航——1,600 多篇散落的 markdown，人工检索靠文件名猜，RAG 召回靠关键词碰运气，同一主题分散在几十篇里。只靠检索算法解决不了「知识组织」问题。

我的做法是加一层 wiki 编译层：LLM 把原始资料离线编译成四类可导航页面（实体 / 概念 / 对比 / 综合），同一概念多源聚合为一页、页面间双向链接、`wiki_schema.md` 作为编译契约注入每次 LLM 调用保证行为一致。编译产物既是人工检索的知识地图，也是 RAG 的召回对象——这就是 raw → wiki → RAG 双轨架构。

检索排序不是查出来就行：生产版已迭代到 v2.4

排序质量直接决定 LLM 拿到的上下文对不对，也就是答案质量的上限。生产版检索器经过四轮迭代：

  • v2.1 准确性加权：标题命中 +60、wiki 层 +40、管理文件 −120，日志待办不再刷屏。
  • v2.2 倒排索引 + 2-gram 候选定位：全库扫描变索引定位，长词短语能连续命中。
  • v2.3 关联页面推荐：命中 wiki 页后聚合双向链接，检索结果不孤立。
  • v2.4 词频饱和 + 业务子库加权：单篇词频贡献封顶（防长文档刷分），自家一手资料优先于二手公开资料。

核心代码思路（零依赖，词频饱和）

词频饱和是 v2.4 最关键的改动：一篇 100 页的长文档重复出现「会员」100 次，一篇 1 页的精准文档出现 3 次——按原始词频排序，长文档永远碾压短文档。这不是「相关」，这是「篇幅优势」。解法是单篇词频贡献封顶：

FREQ_CAP = 10  # 每个查询词在单篇文档的词频贡献封顶

def freq_score(count):
    """词频饱和：超过 FREQ_CAP 后不再线性增加"""
    return min(count, FREQ_CAP)

def score_doc(doc, terms):
    score = 0
    for t in terms:
        score += freq_score(doc.tokens.count(t))  # 词频饱和
    if any(t in doc.title for t in terms):
        score += 60          # 标题命中：强相关信号
    if doc.is_wiki:
        score += 40          # wiki 编译层：LLM 提炼的知识精华
    if doc.is_business:
        score += 25          # 业务子库：自家一手资料优先
    if doc.is_admin:
        score -= 120         # 管理文件：日志/待办/索引降权
    return score

什么时候我会上向量？

不是向量不好，是场景没到。出现下面任一情况，我就会引入向量做混合检索：

  • 语料规模过万，关键词覆盖不过来；
  • 出现"用户问法"和"文档用词"对不上的语义鸿沟；
  • 需要长查询、跨语言、模糊/口语化匹配。

真到那一步，我的做法是本地 embedding + 向量索引 就够，不需要一上来就上重型向量库；再让向量召回和关键词召回做 RRF 融合，变成混合检索。

单用 LLM 会幻觉，单用 RAG 只有文档列表。LLM × RAG 结合，就是让模型「先查资料再回答」——这才是知识库调取的完整闭环。
