我为什么用关键词 + IDF，而不是一上来就向量检索

kb-cli 设计决策 · 约 8 分钟阅读

在 kb-cli 这个项目里，我用的是关键词 AND 匹配 + IDF 加权打分，没有上向量检索。这不是没听过向量、也不是技术债，而是针对我这个具体场景做的选择。下面把踩过的坑、为什么这么选、什么时候会改，一次讲清楚。

先讲我真实踩过的坑：59.8%

最早检索器的排序用的是绝对词频——一个词在某篇文档里出现几次，就给这篇加几分。

拿它跑 2,000 多篇同领域语料，问题非常明显：59.8% 的文档被"运营""管理""系统"这类到处都出现的泛词，压到了同一个主题下面。而真正有区分度的词——"私域""复购""会员码"——反而排不上来。

根因是：绝对词频只奖励"出现得多"，不惩罚"到处都出现"。泛词在每一篇里都出现，于是每一篇都靠它拿高分，文档全塌缩到一起。

修正办法是加 IDF（逆文档频率）：一个词越普遍，它的权重越低；越罕见、越能代表主题，权重越高。改成 TF × IDF 之后，文档被均匀地分散回各自的主题，那个 59.8% 的塌缩就消失了。

那为什么没顺势上向量检索？

向量检索我评估过，但这个场景下有三条理由让我暂时不用：

  • 语料垂直、用词稳定。2,000 多篇都是同领域的中文资料，术语很固定（私域、复购、件单、会员码），关键词召回本来就够用，不存在"用户换个说法就找不到"的问题。
  • 查询都是短的精确查询。"私域分层""复购率怎么算"，用户心里是有关键词的，要的是精确命中，而不是一堆"语义相近"的东西。
  • 要零依赖、可交付。kb-cli 的原则是 clone 下来一行命令就能跑；向量检索要带 embedding 模型和向量索引，正好违背这条。

还有一个额外好处是可解释：业务方看得懂"这篇为什么排前面"——因为命中了哪个罕见词；向量相似度给的是一个数字，业务方没法理解，也没法验证。

核心代码（零依赖，只用标准库）

检索分两步：先做关键词 AND 过滤，再用 TF-IDF 打分排序。math 是 Python 标准库，不引入任何第三方依赖。

import math

def search(query_terms, docs, df, total):
    """docs: [{"id":..., "tokens":[...]}]；df: {词: 含该词的文档数}；total: 文档总数"""
    hits = []
    for doc in docs:
        # 1) 关键词 AND：所有查询词都命中，才入选
        if not all(t in doc["tokens"] for t in query_terms):
            continue
        # 2) TF-IDF 加权打分
        score = 0.0
        for t in query_terms:
            tf = doc["tokens"].count(t)
            idf = math.log((total + 1) / (df.get(t, 0) + 1)) + 1
            score += tf * idf
        hits.append((score, doc["id"]))
    return sorted(hits, reverse=True)

什么时候我会上向量？

不是向量不好，是场景没到。出现下面任一情况，我就会引入向量：

  • 语料规模过万，关键词覆盖不过来；
  • 出现"用户问法"和"文档用词"对不上的语义鸿沟；
  • 需要长查询、跨语言、模糊/口语化匹配。

真到那一步，我的做法是本地 embedding（bge-m3）+ sqlite-vec 就够，不需要一上来就 Milvus；再让向量召回和关键词召回做 RRF 融合，变成混合检索。

没有最好的方案，只有对当前场景最合适、而且自己讲得清原理的方案。
